# Развёртывание экземпляра на po.china-ru.ru — по шагам

Цель — работающий экземпляр платформы для подачи в реестр российского ПО
(ПП РФ № 1236, пункт 5 «б» и доступ для экспертизы). Разворачивается на том
же VPS, где уже работает china-ru.ru на Битриксе.

Выполнять по порядку, не пропуская проверок. Каждый шаг заканчивается
проверкой — если она не прошла, дальше идти нельзя.

|         |                                |
| ------- | ------------------------------ |
| Витрина | `https://po.china-ru.ru`       |
| API     | `https://api.po.china-ru.ru`   |
| Админка | `https://admin.po.china-ru.ru` |

---

## 🔥 Главный риск: действующий сайт

На этом VPS работает боевой сайт компании. Всё, что ниже, задумано так,
чтобы его не трогать, но два места опасны по-настоящему:

1. **Порты 80 и 443** заняты nginx Битрикс-окружения. Наш стек на них не
   претендует — за это отвечает `docker-compose.proxy.yml`. Запуск **без**
   этого файла попытается занять 80/443 и в худшем случае уронит основной
   сайт.
2. **Оперативная память.** Добавляется восемь контейнеров. Если свободной
   памяти мало, ядро начнёт убивать процессы — и выберет не наши, а MySQL
   Битрикса.

Перед началом сделать снимок (snapshot) VPS у хостера. Это минута работы и
единственный способ вернуться, если что-то пойдёт не так.

## Шаг 0. Проверить, что сервер потянет

```bash
free -h                      # свободная память
df -h /                      # свободное место
nproc                        # ядра
docker compose version       # нужна ≥ 2.24 (тег !override в наложении)
ss -tlnp | grep -E ':80 |:443 |:8080 '
```

**Критерии:**

- свободной памяти **не меньше 4 ГБ** — стеку нужно около 3–3,5 ГБ
  (Postgres, Redis, SeaweedFS, Node API, Next.js, два nginx);
- свободного места **не меньше 25 ГБ** — образы, база, загруженные файлы;
- порт `8080` свободен (на нём будет слушать наш nginx);
- Docker Compose версии **2.24 и выше** — см. следующий блок.

Памяти меньше 4 ГБ — **остановиться** и расширить тариф VPS либо брать
отдельный сервер. Запускать «впритык» нельзя: OOM-killer придёт за
действующим сайтом.

### Подкачка на время сборки

Сборка витрины (`next build`) на пике берёт 1,5–2 ГБ сверх работающего
стека. Подкачка не заменяет память, но не даёт этому пику убить MySQL
Битрикса. Если `free -h` в строке `Swap` показывает 0:

```bash
fallocate -l 4G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

**Проверка:** `swapon --show` — строка `/swapfile` размером 4G.

### 🔥🔥 Проверка, которую нельзя пропускать

Наложение снимает у nginx порты 80/443 тегом `!override`. Этот тег
понимают только Docker Compose **2.24 и новее**. Старые версии **не
ругаются** — они складывают списки портов, и наружу уходят и 80, и 443.
То есть ровно то, от чего наложение защищает, причём молча. Проверено на
Compose 2.6.0: вместо одного порта получилось три.

Поэтому проверять надо не версию, а итог склейки:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.proxy.yml \
  --env-file .env.prod config | grep -E 'published: "(80|443)"'
```

**Вывод пустой — можно продолжать.** Что-то нашлось — **стоп**: обновить
Docker Compose и повторить. Запуск в этом состоянии попытается занять
порты действующего сайта.

## Шаг 1. DNS

Три A-записи на IP этого VPS:

```
po.china-ru.ru          A    <IP>
api.po.china-ru.ru      A    <IP>
admin.po.china-ru.ru    A    <IP>
```

Можно одной записью `*.po.china-ru.ru` плюс `po.china-ru.ru`.

**Проверка** (ждать, пока все три отдадут нужный IP):

```bash
dig +short po.china-ru.ru api.po.china-ru.ru admin.po.china-ru.ru
```

Пока DNS не разошёлся, шаг 4 (сертификат) не пройдёт — Let's Encrypt должен
достучаться до сервера по этим именам.

## Шаг 2. Код на сервере

Ветка `main` должна быть в GitHub. **Пушить своими учётными данными** —
у токена Клода нет права записи в `.github/workflows/`:

```bash
# на рабочей машине
git push origin main
```

На сервере:

```bash
cd /opt
git clone git@github.com:<владелец>/<репозиторий>.git china-ru
cd china-ru
git log --oneline -1          # сверить, что это нужный коммит
```

## Шаг 3. Настройки

```bash
cp .env.prod.example .env.prod
chmod 600 .env.prod
nano .env.prod
```

Заполнить:

| Переменная           | Значение                                                  |
| -------------------- | --------------------------------------------------------- |
| `POSTGRES_PASSWORD`  | `openssl rand -hex 24`                                    |
| `JWT_ACCESS_SECRET`  | `openssl rand -hex 32`                                    |
| `JWT_REFRESH_SECRET` | `openssl rand -hex 32` — **другой**, не копия предыдущего |
| `S3_SECRET_KEY`      | `openssl rand -hex 24`                                    |

Домены в примере уже проставлены под `po.china-ru.ru` — менять не нужно.

🔥 `COOKIE_DOMAIN=po.china-ru.ru`, а **не** `china-ru.ru`. Апексный домен
означал бы, что браузер шлёт refresh-токены платформы действующему сайту на
Битриксе при каждом обращении к нему. Умолчаний у этих переменных в
`docker-compose.prod.yml` больше нет — пустая переменная уронит запуск с
понятной ошибкой, и это правильно.

## Шаг 4. Сертификат

Выпускается на хосте, одним на три домена. Каталог certbot назовёт по
первому имени — именно оно должно стоять в `CERT_NAME`.

Сначала nginx хостинга должен отдавать проверку ACME по этим доменам —
за это отвечает HTTP-часть конфига. Вторая часть (`china-ru-app.conf`)
ссылается на файлы сертификата и до выпуска не пройдёт `nginx -t`,
поэтому она — в шаге 5.

```bash
mkdir -p /var/www/certbot

# Битрикс-окружение (каталог называется «avaliable» — опечатка штатная)
cp infra/host-nginx/china-ru-acme.conf /etc/nginx/bx/site_avaliable/
ln -s ../site_avaliable/china-ru-acme.conf /etc/nginx/bx/site_enabled/
nginx -t && systemctl reload nginx

# если certbot не установлен (Битрикс-окружение на CentOS/AlmaLinux)
dnf install -y certbot

certbot certonly --webroot -w /var/www/certbot \
  -d po.china-ru.ru -d www.po.china-ru.ru \
  -d api.po.china-ru.ru -d admin.po.china-ru.ru
```

**Проверка:**

```bash
ls -l /etc/letsencrypt/live/po.china-ru.ru/
```

Если каталог назвался иначе — поправить `CERT_NAME` в `.env.prod` и пути в
конфиге из шага 5.

⚠️ Если выпуск упал на проверке — DNS ещё не разошёлся (шаг 1) либо
HTTP-часть не включилась: `curl -I http://po.china-ru.ru/.well-known/acme-challenge/x`
должен отдать 404 от nginx, а не переадресацию на действующий сайт.

## Шаг 5. Конфиг nginx хостинга

```bash
# Битрикс-окружение
cp infra/host-nginx/china-ru-app.conf /etc/nginx/bx/site_avaliable/
ln -s ../site_avaliable/china-ru-app.conf /etc/nginx/bx/site_enabled/

# обычный nginx (Ubuntu/Debian) — то же для обоих файлов:
# cp infra/host-nginx/china-ru-{acme,app}.conf /etc/nginx/sites-available/
# ln -s ../sites-available/china-ru-acme.conf /etc/nginx/sites-enabled/
# ln -s ../sites-available/china-ru-app.conf /etc/nginx/sites-enabled/

nginx -t && systemctl reload nginx
```

🔥 `nginx -t` обязателен до `reload`. Битый конфиг при перезагрузке положит
действующий сайт. Если `nginx -t` ругается на `http2` — nginx хостинга
старше 1.25.1: убрать строки `http2 on;` и писать `listen 443 ssl http2;`.

## Шаг 6. Запуск стека

Ещё раз убедиться, что наложение сработало (проверка из шага 0, вывод
обязан быть пустым):

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.proxy.yml \
  --env-file .env.prod config | grep -E 'published: "(80|443)"'
```

**Оба файла, наложение вторым.** Образы собираются по одному: по умолчанию
compose собирает их параллельно, и три сборки Node разом рядом с Битриксом
в память не помещаются.

```bash
compose="docker compose -f docker-compose.prod.yml -f docker-compose.proxy.yml --env-file .env.prod"
$compose build api
$compose build web
$compose build admin
$compose up -d
```

Сборка на двух ядрах — 20–40 минут, дольше всех витрина. Пока она идёт,
в соседнем окне держать `free -h` и проверять `https://china-ru.ru`.

**Проверка:**

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.proxy.yml ps
curl -s http://127.0.0.1:8080 -H 'Host: po.china-ru.ru' -o /dev/null -w '%{http_code}\n'
curl -s https://api.po.china-ru.ru/api/health
```

Все контейнеры в состоянии `running`, у api — `healthy`. Health-проверка
отдаёт признак готовности.

🔥 Пропустить `-f docker-compose.proxy.yml` — значит попытаться занять
80/443 и получить «address already in use», а при неудачном стечении
обстоятельств задеть основной сайт.

### Наполнение базы справочными данными

Без категорий каталога продавец не может завести товар: кнопка «Добавить
товар» в кабинете выключена. Наполнение идемпотентно, повторять можно:

```bash
$compose exec api node apps/api/dist/seed.js
```

## Шаг 7. Пройти документ 02 руками

**Это не формальность.** `docs/registry/02-ustanovka-i-ekspluataciya.md`
опубликован на china-ru.ru и по нему пойдёт эксперт. Инструкция написана по

Пройти её по шагам и записать каждое расхождение: другое имя переменной,
пропущенная команда, иной вывод. Поправить документ **и переопубликовать**
на china-ru.ru.

Неработающая опубликованная инструкция хуже, чем её отсутствие: эксперт
проверяет именно по ней.

## Шаг 8. Демонстрационные данные и учётки

Пустая витрина читается как незавершённый продукт, даже если код полон.

Нужно:

- категории и товары в каталоге — столько, чтобы работали листание и фильтры;
- хотя бы один оформленный заказ, чтобы в кабинете продавца было что показать;
- три учётные записи: **покупатель**, **продавец**, **администратор**.

Логины и пароли записать — они идут в заявление, раздел 6.

## Откат

Если что-то пошло не так, стек снимается целиком и бесследно для основного
сайта:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.proxy.yml down
rm -f /etc/nginx/bx/site_enabled/china-ru-app.conf /etc/nginx/bx/site_enabled/china-ru-acme.conf
nginx -t && systemctl reload nginx
```

Данные остаются в томах Docker. Удалять их (`down -v`) только осознанно —
это снос базы.
